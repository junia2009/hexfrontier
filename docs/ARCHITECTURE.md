# アーキテクチャ

本作の設計原則・状態機械・モジュール構成・レンダラー・CPU・テスト戦略をまとめる。
ルールの仕様(公式との差分)は [RULES.md](RULES.md)、作業手順は [../CLAUDE.md](../CLAUDE.md) を参照。

## 設計原則

1. **ルールエンジンと描画の完全分離**
   `src/rules/` と `src/actions.js` は DOM / canvas / Three.js に一切依存しない純粋な
   JavaScript。`node --test` だけで全ルールが検証でき、セルフプレイも Node 単体で回る。
2. **単一のシリアライズ可能な GameState**
   ゲームの全情報は 1 つの plain object。`structuredClone` / `JSON.stringify` がそのまま通る
   (Map / Set / クラスインスタンスは使わない)。ID は文字列キーの plain object で引く。
3. **決定性**
   乱数は全て `state.rng`(シード付き mulberry32)経由。同じシード + 同じアクション列は
   必ず同じ結果になる。これがテスト・再現・デバッグの土台。
4. **ビルド工程なし**
   ES Modules を直接ブラウザで読む。Three.js は `vendor/` にベンダリングし importmap で解決。

## 盤面の形(`src/rules/board.js`)

盤の**幾何**と、**どのヘックスを実際に使うか**を分けている。

- `LAYOUT` … ヘックス・頂点・辺の隣接表。モジュール定数として一度だけ構築する。
  幾何しか持たないので、使いうる最大半径(`MAX_BOARD_RADIUS = 4`、61ヘックス)まで作っておく。
- `board.hexIds` … その対戦で実際に使うヘックスのID列。基本の盤は半径2の19ヘックス。
  **盤の形を変えられるのはここだけ**で、モードごとに違う形の盤を作れる。
- 頂点・辺・海岸辺は `board.hexIds` から導出する(`boardVertexIds` / `boardEdgeIds` /
  `coastalEdgesOf`)。導出結果はヘックスID列をキーにメモ化してあり、**state には持たせない**
  ── オンライン対戦は毎手番 state を配るので、頂点IDの配列を積むと通信量が跳ね上がるため。
- 盤が広いモードでは描画側も追随する: 2D は `computeView` が余白を詰め、
  数字トークンを相対的に大きくして pips を省く。3D はカメラを盤の広さ(`boardK`)ぶん引き、
  トークンのメッシュを拡大する。既存モードは `boardK = 1` なので一切変わらない。

`LAYOUT` の並び順は「基本の盤 → その外側」。こうすると頂点IDや辺IDの列が
基本の盤のものと**完全に前方一致**するので、盤を広げても既存モードの同点処理
(先に見つけたものを採る)が一切変わらない。`test/board-regression.test.js` が
モード×シードごとに盤面と対戦の全展開をハッシュで固定しており、
ここを触って既存モードの挙動が変わったら落ちる。

`LAYOUT.vertexHexes` / `LAYOUT.hexNeighbors` には盤外のヘックスも入るので、
盤の中身を引くときは `vertexHexesOf(board, vid)` / `hexNeighborsOf(board, hid)` を使う。

## アクションパイプライン

全ての状態変更は 1 本道:

```
dispatch(state, action)
  ├─ validateAction(state, action)  … 純粋関数。エラーなら日本語の理由文字列、OKなら null
  ├─ structuredClone(state)         … 元の state は不変
  └─ applyAction(clone, action)     … クローンに適用して返す
```

- `validateAction` は UI のボタン活性判定にもそのまま使う(エンジンと UI で判定が一致)。
- CPU も人間も同じ `dispatch` を通る。CPU は `chooseAction(state, pid)` が action を返すだけ。

### アクション一覧(`src/actions.js`)

| 分類 | アクション |
|---|---|
| 共通 | `PLACE_INITIAL` `ROLL_DICE` `DISCARD` `MOVE_ROBBER` `BUILD_ROAD` `BUILD_SETTLEMENT` `BUILD_CITY` `TRADE_BANK` `END_TURN` |
| 交易 | `OFFER_TRADE`(全員へ一斉提案) `RESPOND_TRADE` `CHOOSE_TRADE`(応じた中から相手を決める) |
| 基本のみ | `BUY_DEV_CARD` `PLAY_DEV_CARD` |
| 都市と騎士 | `BUILD_KNIGHT` `ACTIVATE_KNIGHT` `PROMOTE_KNIGHT` `MOVE_KNIGHT` `CHASE_ROBBER` `BUILD_WALL` `BUY_IMPROVEMENT` `PLAY_PROGRESS_CARD` `RAZE_CITY` `PICK_AQUEDUCT` |
| ドラゴンの島 | `BUILD_TOWER` |
| 漁師たち | `SPEND_FISH`(魚を使う) `PASS_SHOE`(古い靴を渡す) |
| 航海者たち | `BUILD_SHIP` `MOVE_SHIP` `PICK_GOLD`(金鉱の資源選択) |

### 割り込み(awaiting 状態機械)

手番の通常フローを中断する処理は `state.awaiting = { type, players, context }` で表現する。
`awaiting` が非 null の間は、`players` に含まれるプレイヤーの該当アクションしか通らない。

| type | 発生元 | 解決アクション |
|---|---|---|
| `setupPlacement` | 初期配置(スネーク順) | `PLACE_INITIAL` |
| `discard` | 7ロール / 破壊工作員(`context.cause` で区別) | `DISCARD` |
| `moveRobber` | 7ロール / 騎士追い払い | `MOVE_ROBBER` |
| `barbarianDefense` | 蛮族侵攻で敗北した都市所有者 | `RAZE_CITY` |
| `tradeOffer` | 交易の一斉提案(提案者以外の全員が待ち) | `RESPOND_TRADE` |
| `tradeChoose` | 一斉提案に2人以上が応じた(提案者が待ち) | `CHOOSE_TRADE` |
| `aqueduct` | 水道橋(科学Lv3)所持者が無産出の出目 | `PICK_AQUEDUCT` |

複数プレイヤー待ち(捨て札など)は `players` 配列から解決済みを取り除き、
空になったら次の状態へ遷移する。

## GameState の主なフィールド(`src/state.js`)

```js
{
  seed, mode,              // 'base' | 'cak' | 'dragon'
  difficulty,              // 'easy' | 'normal' | 'hard'(CPU評価ノイズ量)
  rng,                     // mulberry32 の内部状態(数値)
  phase,                   // 'setup' | 'main' | 'ended'
  turn, currentPlayer,
  awaiting,                // 上記の割り込み(null = 通常フロー)
  board,                   // hexIds・hexes(terrain/token)・robber・ports
                           //  + fisheries/lake(漁師たち)
                           //  + pirate/islandOf(航海者たち)
  buildings, roads,        // vertexId/edgeId -> { player, ... }
  ships,                   // edgeId -> { player, builtTurn }(航海者たち)
  players: [{ resources, devCards, commodities, improvements,
              progressCards, progressVP, defenderPoints, treasures, fish, islands, ... }],
  bank,                    // resources 各19・devDeck・commodities 各12・progressDecks・fishPool
  dice, eventDie,          // eventDie は cak のみ('ship' | 各進歩デッキ)
  diceMode, diceDeck,      // 'random'(毎回独立。既定) | 'balanced'(36通りの山札から引く)
  diceCounts,              // 出目(2〜12)が何回出たか。📊の棒グラフに使う
  turnFlags,               // rolled / playedDev / fleet / offers / alchemist ...
  longestRoad, largestArmy,
  knights, walls, merchant, barbarians, metropolis,   // 都市と騎士
  dragon, towers, burned,                             // ドラゴンの島
  // 漁師たち: 魚は players[].fish(公開)と bank.fishPool のみ。専用のトップレベル状態はない
  winner, log,
}
```

`src/rules/` と同じく「両方が取り込む共有のコード」として `src/` に置く。

`server/` は `src/rules/` と `src/actions.js` をそのまま取り込む(wrangler が
バンドルする)。**ルールエンジンを直したらサーバーも再デプロイが要る** ──
`.github/workflows/server.yml` の paths に `src/**` が入っているので自動で走る。

### 進歩カードのプラグイン構造

54枚(25種)は `PROGRESS_CARDS[id]` の宣言的定義に集約:

```js
{ deck, count, name, icon, desc,     // メタ情報(UI・説明書はここから自動生成)
  needsParams,                       // UI がどの入力モードを開くか
  preRoll?, vp?,                     // ロール前使用可(錬金術師)/ 勝利点カード
  validate(state, pid, params),      // エラー文字列 | null
  play(state, pid, params) }         // 効果適用
```

CPU 側も同じ思想で `progress-ai.js` の `SCORERS[id]` に「今使うと何点相当か」を
カード別に実装し、`pickProgressPlay` が難易度別の閾値と比較して使用を決める。
新カードの追加 = 定義 1 つ + スコアラー 1 つ。

## CPU(`src/ai/`)

`chooseAction(state, pid)` の優先順:

1. **awaiting の解決**(初期配置 / 捨て札 / 盗賊 / 都市破壊 / 交易応答 / 水道橋)
2. ロール前: 錬金術師の使用判断(cak)
3. ロール
4. メインフェーズ(貪欲法): 進歩カード使用 → 都市化 → 開拓地 → 騎士(蛮族対応)→
   都市改良 → 見張り塔(dragon)→ 道 → 発展カード → 銀行/プレイヤー間交易 → 手番終了

- 評価は `evaluator.js` の盤面スコア(生産力・勝利点・多様性)+ 目標(nextGoal)への距離。
- **難易度**は評価値への決定的ノイズで実現: `evalNoise(state, key)` が
  シード・手番・候補キーの FNV 風ハッシュから擬似乱数を作り、
  振幅 0(強い)/ 0.9(普通)/ 3.0(弱い)で加算する。state の rng を消費しないため
  難易度が変わってもゲームの乱数列は同一。
  交易の応諾マージンとカード使用閾値も難易度で変わる。
- プレイヤー間交易: 誰であれ `OFFER_TRADE` で**全員に一斉提案**し、返事が揃ってから相手を決める。
  CPU は誰が何を持っているかを見ずに提案し(人間の手札を覗かないため)、
  空振りは「1手番1回・1巡あけ(全員に断られたら2巡)」の自制で抑える。

## レンダラー

`viewMode`('3d' | '2d')で切替。両者とも「state を受けて全体を再描画」する冪等な設計で、
差分管理はキャッシュキーで行う。

### 2D(`render/board-render.js`)

静的な盤面(ヘックス・港・数字)はオフスクリーン canvas に一度だけ描き、
キー `${seed}:${board.version}:${w}x${h}@${dpr}` が変わるまで再利用。
動的要素(建物・コマ・ハイライト)は毎フレーム上書き。

### 3D(`render3d/board3d.js`)

- **staticGroup**: 地形・海・装飾。キー `${seed}:${mode}:${board.version ?? 0}` で再構築。
- **dynamicGroup**: 建物・騎士・塔など。state のキー列を diff して増減分だけ生成/破棄。
- **海**: カスタム ShaderMaterial。盤のヘックス中心への最短距離で深度グラデーション、
  value ノイズの波・岸辺の泡・雲影・頂点うねり。影は同一ジオメトリの
  ShadowMaterial(`seaShadowMat`)を重ねて受ける。
- **空**: BackSide の球に地平線→天頂グラデーション+太陽グロー+ハッシュ星空。
  `SKY_CYCLE_SEC = 300` 秒で昼夜サイクル。`SKY_PHASES` のキーフレームを補間し、
  太陽光の位置/強さ・半球光の色(夜は月明かり色)・フォグ・海の色・影の濃さを同期。
  半球光は**上からの色(`hemiC`)と下からの色(`hemiG`)を別々に**動かす。
  夜に地面が見えないのは、空を向いていない面(崖・タイルの側面)に光が
  当たらないせいなので、`hemiG` を上げないと月明かりだけ強くしても効かない。
- **光る苔**(`addMoss` / `buildMoss` / `makeMossHalo`): 夜の道しるべ。
  砂漠以外の全ヘックスに撒く。**2枚重ねで作る**:
  - **粒**: 実体(`GEO.moss` の正二十面体)。昼は苔むした地面、夜は
    `emissive` を `_tickSky` が `night × MOSS_GLOW` で立ち上げる光の芯。
  - **光暈**: 地面に寝かせた板を加算合成で光らせる自前のシェーダー。
    中心から外へなめらかに減衰し、粒ごとの位相でゆっくり明滅する。
    `night^1.5 × MOSS_HALO`(粒より遅れて灯る)。
  どちらも1枚のインスタンスにまとめてあるので、描画呼び出しは合計2回。
  **見た目で外してはいけない3点**(全部いちど外して「汚物みたい」と言われた):
  - **輪郭を立てない。** 実体だけだとふちが硬く出て、光ではなく塗料に見える。
    滲み(光暈)が要る。
  - **白飛びさせない。** 芯が飛ぶと色が抜けて白い染みになる。`MOSS_HALO` は
    「上げても光る面積が増えず芯だけ飛ぶ」手前で止めてある。
  - **べったり敷き詰めない。** 株は中心ほど密に撒いてふちを溶かし、
    株どうしのあいだには暗い地面を残す。暗がりがあってこそ光が光に見える。
  実装上の落とし穴が2つ:
  - 苔は地面に貼りつく小ささなので、`TILE_TOP` 決め打ちだと**起伏に埋まって
    消える**。`capHeight()`(描いてある三角形の上を読む)で載せる。
  - 光暈の板は平らなので、そのままだと起伏にめり込んで欠ける。板の大きさに
    比例して持ち上げる(実測: 持ち上げなしだと 27% しか出ない)。
- **影**(`src/shadow-fit.js` + `Board3D._placeSun`): 平行光源1本の影マップ。
  「キャラの影がなびいて・チカチカして安定しない、しかも薄い」という報告を
  直したときに、**三つとも別の理由で壊れていた**ことが分かった。
  - **`bias` は奥行きの深さで効き目が変わる。** これが「薄い」の主犯。
    three の `shadow.bias` は深さを 0〜1 で見た値なので、影カメラの
    奥行き(既定 near 0.5 / far 500 = 499.5)を掛けたぶんだけ影が奥へ下がる。
    `-0.0004` は**ワールドで 0.2 単位**。身長 0.9 単位のキャラの足元の影は
    それでほとんど削れ、残りかすだけがチラついていた。
    太陽を `SUN_DIST = 18` に置いて near 1 / far 39.6 に詰め、同じ効き目を
    1/13 の値でまかなう。
  - **箱が大きすぎた。** 影の箱(平行投影)は島ぜんぶを入れる ±15。
    2048 の影マップだと 1 単位あたり 68 テクセルしかなく、腕の太さ
    0.05 単位は 3 テクセル。歩くたびに升目に入ったり出たりして明滅する。
    歩きモードだけ箱を**主役の足元に寄せて ±5**(205 テクセル/単位)にする
    (`setShadowFocus()` に「いまどこか」を返す関数を渡す。値で渡すと
    `_tickSky` が `onFrame` より先に走るぶん1フレーム遅れる)。
  - **箱が升目の上を滑っていた。** 太陽は 300 秒で空を巡るので箱は毎フレーム
    少し動く。テクセル半個ぶんのずれが残ると輪郭が升目の境目を行き来して
    ゆらゆらする。箱の中心を**影カメラの基底の上で升目に吸着**させると、
    ずれが「0 か 1 テクセル」に量子化されて止まる(`snapFocus`)。
    基底は THREE の `Object3D.lookAt` と同じ作り方でないと升目がずれる。
  `normalBias` は箱の大きさに比例させる(にじみ幅はテクセル何個ぶんで
  決まるため)。固定値だと細かいほうで縞が出るか、粗いほうで影が浮く。
  実測(真上から、同じ島・同じ立ち位置、少しずつ動かしながら6回):
  影の面積 739 → 1699 px、面積の振れ 9% → 1%、いちばん濃いところ 75% → 46%。
  なお `THREE.PCFSoftShadowMap` は r185 で非推奨になっていて、
  内部で `PCFShadowMap` に落ちる(コンソールに警告が出る)。
- **地形**: ヘックスごとに6セクターを重心細分(N=4)した非インデックス
  BufferGeometry。頂点座標のハッシュで隣接ヘックスと継ぎ目を一致させる(watertight)。
- **演出**: ドラゴンの飛翔→火炎ブレス→着火のチェーン、蛮族船の航路航行、
  3D ダイスの転がり、交易バナー等。演出中も state は既に確定済み
  (描画が後追いするだけで、ロジックは待たない)。
- **手番の合図**(`maybeTurnFx`): 手番が移るたびに「誰の番か」を出す。
  他人は上寄せの小さいピル、自分だけ中央に大きく + 色帯。
  一瞬で消えるので、自分の番のあいだは `body.myturn` で
  盤面のフチと自分のプレイヤーチップを光らせ続ける。
  `refresh()` から呼ばれ、**手番の鍵**(setup は配置順、main は `turn`+`currentPlayer`)が
  変わったときだけ出すので、割り込みや再描画では鳴らない ──
  ローカル戦・CPU・オンラインのどれでも同じ経路で動く。

## 画面の向き(縦横の切り替え)

端末を回すと配置が大きく変わる。**ここは三か所とも別々の理由で壊れていた**ので、
直しかたと理由を残す(`test/layout.test.js` が静的に見張っている)。

- **中央寄せは `safe center` にする。** `.screen` は `position: fixed` で
  中身を中央に置いているが、**中身が画面より高いとき、ただの `center` だと
  はみ出したぶんがスクロールしても届かない場所へ行く**(フレックスの
  中央寄せの罠)。横向き 844x390 で選択パネルがこれに当たり、
  **「ゲームを始める」ボタンに触れなくなっていた**。
  `safe center` は収まらないときだけ先頭寄せに切り替わる。
  あわせて `overflow-y: auto` が要る(先頭寄せでも、スクロールできなければ届かない)。
- **モバイル判定は幅だけで決めない。** `max-width: 820px` だけだと、
  端末を横にした 844px 幅がこの条件から外れて、スマホなのに机上向けの
  配置になる。縦に詰まった画面に縦長前提の配置が入るので収まらず、
  盤が 544x159 まで潰れていた。`max-height` も足して、
  背の低い画面はモバイル配置にする。
- **構図の取り直しは「形が大きく変わったとき」だけ**(判断は `src/view-fit.js`)。
  `_fitCamera` はカメラの距離を計算し直して置き直すので、呼ぶたびに
  寄り引きが起きる。**高さが少し動くたびに呼ぶと画面が脈打つ** ──
  実機では横から縦に戻したあと URL バーが出入りして高さが何度も変わるので、
  これが「ブルブル揺れてズレる」の正体だった(高さ 844↔788 の揺れで、
  カメラ距離が 19.12↔17.85 と往復していた)。
  画面の形に合わせる(`setSize` と `camera.aspect`)のは毎回やってよい ──
  **カメラを動かさないので揺れない**。動かすほうだけ止める。
  縦横の境目にはヒステリシスを入れる(入る線 0.8 / 出る線 0.95)。
  ここをまたぐと盤の見せ方が 90° 回るので、境目ちょうどで揺れると
  盤がくるくる回ってしまう。
- **2D の盤は入れ物を `ResizeObserver` で見張る。** `resizeCanvas()` は
  描画ループの中でしか呼ばれず、そのループは光るものが無ければ止まる
  (`animLoop` の `hasPulse`)。`window` の `resize` を取りこぼすと、
  キャンバスの画素数だけ古いまま残って CSS に引き伸ばされ、盤がゆがむ。
  **取りこぼしは普通に起きる** ── 端末の回転では最終的な配置が決まる
  前に `resize` が飛ぶことがあり、`dvh` の変化(URL バーの出入り)では
  飛ばないこともある。3D は同じ理由で最初から `ResizeObserver` を使っている。

調べかたの注意:
- **「回したら壊れた」は対照実験で確かめる。** 海が消えたように見えたが、
  回さずに同じ時間だけ置いた画と比べたら差は 6.09% 対 6.08% で、
  ただの波と雲の動きだった。回転のせいだと思い込んで追いかけると遠回りする。
- **測る直前に画面を変えない。** `goto` の直後に大きさを変えて測ると、
  配置が終わる前の値を拾って「454px はみ出している」のような幻を見る。
- **「画面の外にある」と「届かない」は別。** 画面より高いパネルは
  はみ出して当たり前で、欠陥なのは**スクロールしても届かない**とき。
  祖先にスクロールできる箱があるかまで見ること。

## オンライン対戦(`server/`)

合言葉(英字4文字)を共有した最大4人で遊ぶ。**サーバー権威型**で、
クライアントはルール判定も乱数も持たない。

```
ブラウザ ──action──▶ Worker ──▶ Durable Object(合言葉ごとに1つ)
   ▲                              │ RoomCore が dispatch() で適用
   └──── 席ごとに伏せた state ─────┘
```

### なぜサーバーでも同じエンジンが動くのか

`src/rules/` と `src/actions.js` は DOM 非依存の純粋関数なので、
Durable Object がそのまま `import` して使える。**ルール実装は 1 つだけ**で、
クライアントとサーバーで 実装の食い違いが起きない。

| ファイル | 役割 |
|---|---|
| `server/room-core.js` | 部屋のロジック(席・ホスト・開始・アクション適用・伏せ処理・肩代わり)。**WebSocket に非依存**なので `node --test` で直接検証できる |
| `server/room-do.js` | Durable Object。WebSocket 接続を RoomCore に繋ぎ、誰に何を送るかを決める |
| `server/index.js` | Worker。`/new` で合言葉を発行し、`/room?code=` を DO へ振り分ける |
| `server/walk-relay.js` | 散策部屋の位置の中継。溜めて一定間隔でまとめて配る(下の節) |
| `src/minigame/meet/*` | 集まりの進行。サーバーが取り込んで回すが、ひとりのときは手元で回す |
| `src/net/client.js` | ブラウザ側。接続・再接続・端末IDの保持 |

### メッセージ

| 向き | 種類 | 内容 |
|---|---|---|
| C→S | `hello` | 端末IDと名前。席の割り当て(再接続なら元の席) |
| C→S | `settings` / `start` | ホストのみ。ルール・空席のCPU補完・開始 |
| C→S | `action` | 自分の席の手。`player` が自席と違えば拒否 |
| C→S | `ping` | 接続維持(25秒ごと) |
| S→C | `joined` / `lobby` | 席番号、参加者一覧、ホスト、設定 |
| S→C | `state` | 版番号 + **その席から見た**状態 + 直前に適用されたアクション(演出の再生用) |
| S→C | `error` | 却下理由。食い違い防止に正しい状態を送り直す |

状態は 11KB 程度しかないので、差分同期はせず**毎手ごとに全状態を配る**。
取りこぼしても次の手で必ず追いつく。

### 隠し情報

`viewFor(seat)` が席ごとに伏せた状態を作る。描画側は相手の手札を枚数でしか
読まないため、中身を差し替えても表示は壊れない。

- 他プレイヤーの `devCards` / `progressCards` → 同じ枚数の `hidden` に置換
- 他プレイヤーの `resources` / `commodities` → **内訳を 0 にして** 実際の枚数を
  `hiddenCards` に移し、`hidden: true` を立てる。枚数だけは公開情報(7の捨て札や
  略奪相手の選択に使う)なので `totalCards()` が `hiddenCards` を足して見え方を揃える
- `bank.devDeck` / `progressDecks` → 中身を `null` に(枚数は購入可否の判定に必要)
- `state.rng` → `0`(未来の出目を予測させない)
- `state.diceDeck` → 中身を `null` に(**残り枚数は公開情報**なので長さは保つ)
- **決着後は全公開**(隠し勝利点を含む最終得点を正しく出すため)

伏せた手札は、クライアント側の先読み判定(`validateAction` を手元でも通して
無駄な往復を減らす仕組み)から見ると「持っているか分からない」状態になる。
`handHidden(player)` が真のときは手元では判定を通し、可否はサーバーに任せる。

#### 相手の手札を覗くカード(豪商・スパイ)

覗いた中身を `awaiting.context` に入れると**全席に配信されてしまう**。
context には「誰の何を開くか」だけを置き、`viewFor(seat)` が
覗く本人の配信でだけ伏せを外す(豪商は手札、スパイは進歩カードだけ)。

### 放置された部屋の自動切断

Durable Object は WebSocket が繋がっている間ずっとメモリに常駐し、その時間が
そのまま無料枠(13,000 GB-s/日)を消費する。開いたまま放置されたタブが
枠を食い潰さないよう、**1時間操作がなければサーバーから切断する**。

- 「操作」に数えるのは**人の意思がある行為だけ**(参加・設定変更・開始・手を出す)。
  接続維持の ping と CPU の自動進行は数えない ── これを数えると放置が永久に延命される
- 切断時は `fatal: true` を付けて通知する。クライアントは自動再接続せず、
  理由を表示して合言葉の画面に戻る(すぐ入り直せる)
- 誰も繋がっていない部屋では CPU の自動進行も止める(無人の対局で常駐しない)
- 上限は `IDLE_DISCONNECT_MS` 環境変数で上書きできる(E2E で短縮するため)

### 切断と再接続

端末IDを localStorage に持ち、同じIDで戻れば元の席に復帰する。
切断中の席はサーバーが CPU として肩代わりして進めるので、
誰かが落ちてもゲームは止まらない。ホストが抜けたら次の接続者がホストになる。
対戦中の部屋には新しい人は入れない。

### 権限の境界

- 席の手は**自分の席のものしか出せない**(`action.player !== seat` は拒否)
- ルール判定は `validateAction` がサーバーで必ず走る(クライアントの検証は往復を減らす早期リターンにすぎない)
- ルール・難易度・開始はホストのみ

### 散策部屋(`kind: 'walk'`)

同じ合言葉で集まって、対戦せずに島を歩く部屋。盤は「種 + 島の種類」から
**各自が同じ引数で作る**ので、サーバーは盤を持たない。

- **位置は中継するだけ**(`walk-relay.js`)。届いた位置を溜めて 10回/秒で
  「全員ぶん1通」にして配る。宛先ごとに作り分けない(自分の席を飛ばすのは
  受け取った側の仕事)── N人に N通ずつ作ると N×N になる。
- 位置は **storage に書かない**。次の瞬間には古くなる値なので、書くと遅くて高いだけ。

#### 集まり(大会)

島ごとに何が開かれるかは `src/minigame/meets.js` の表**1か所**で決まり、
サーバーとクライアントの両方がそこを見る(受付が立たない島で大会が始まる、
という食い違いを防ぐ)。表に足したら `room-do.js` の `ENGINES` にも足すこと ──
`test/meets.test.js` がその食い違いを見張っている。

| 島 | 開かれるもの | 誰が進行を持つか |
|---|---|---|
| 基本 | 大富豪 | 配り・手番・順位を全部サーバー。**手札は席ごとに伏せて配る** |
| 漁師たち | つり大会 | 締め切りと順位。**釣果はクライアントが申告**(魚の抽選は端末側) |
| ドラゴン | ドラゴンから逃げろ | 竜の位置も当たり判定もサーバー。端末ごとに竜の居場所が違うと揉める |
| 都市と騎士 | 蛮族を射る | 波の**種**を配る。点はクライアントが申告(当たり判定は端末側) |
| 航海者たち | 丸太乗り | 丸太の**種**と浮かべた場所を配る。**落ちたのはクライアントが申告**(時刻はサーバーが打つ) |

- **締め切りと順位はサーバーが決める。** 端末の時計のずれや切断で
  「どっちが勝ったか」が食い違わないように、`view()` を全員に配る。
- 順位の付け方(`src/minigame/contest.js`)は**サーバーとクライアントで同じ1本**を通す。
  同着は同率(1,1,3)。席番号は表に並べる順を決めるだけで、順位には効かせない。
- クライアントが申告するものには壊れた値よけを置く(上限・間隔・単調増加)。
  友達どうしで遊ぶ前提なので、それ以上の対策はしていない。
- 秒に何度も届く申告は `quiet` を返し、**配り直しも保存もしない**。
  順位表を秒に何度も描き直すと実機の指が効かなくなるし(`src/render/dom.js`)、
  当たるたびに storage へ書くのは高い。1秒ごとの tick が同じ表を運ぶ。
- 大会の通算と実績は端末のローカル(`progress.js` の `meets`)。サーバーは持たない。
- **遊びを足したら `contestOutcome`(`minigame/contest.js`)にも足すこと。**
  ここが「その回の優勝・記録・順位」を決めていて、**知らない kind は
  釣り大会あつかいで落ちてくる**。丸太乗りを足したときは気づかず、
  存在しない `me.cm` を見て**優勝が一度も記録されず、順位も全員1位**に
  なっていた(実測)。順位表は正しく出るので画面では気づけない ──
  戦績を開いて初めて分かる類のバグなので、テストで押さえる
  (`test/logroll.test.js` の「回の結果が順位と記録になる」)。
  記録の単位(`score`)も遊びごとに違う ── 釣りは cm、竜と丸太は秒、
  蛮族は点、大富豪は卓の人数。`src/render/records.js` の表と
  `achievements.js` の `checkMeet` にも1行ずつ要る。
- **実績の入口は4つある**(`achievements.js` の `OTHER_GATES`)。
  対戦の締め(`unlockedBy`)のほかに、集まりの結果(`checkMeet`)、
  島で見つけたもの(`checkSeen`)、蛮族のひとり記録(`checkRaid`)、
  港での釣り(`checkFish`)。**入口を足したら `OTHER_GATES` にも足す** ──
  そこに無いと「対戦を1戦終えたら付く」ほうに混ざる。
  一覧はテストも読むので、書き写さないこと。
- **判定を書いただけでは付かない。** 記録を足す関数(`addCatch` /
  `addContestResult` / `addRaidRun` / `noteSeen`)がその入口を呼んで
  はじめて解除される。図鑑は長らく判定も入口も無く、21種の魚を集めても
  何も起きなかった ── `test/progress.test.js` の
  「魚を釣ると図鑑の実績が積まれる」がその配線を見張る。
- **実績を後から足したら、すでに達成しているぶんにも行き渡らせる。**
  4つの入口はどれも「その遊びを次に終えたとき」しか走らないので、足した
  だけでは条件を満たしている人に付かない ── 竜から5回逃げきっている画面に
  「5/3回」と出たまま鍵がかかっていた。`loadProgress` が
  `reconcileAchievements` を通して、保存してある記録と突き合わせて埋める。
  対戦の締め(`unlockedBy`)も埋める ── 1戦ぶんの記録(`games`)に `marks`
  ごと残してあるので、そこを順に通せば同じ判定ができる。**しきい値を
  緩めたときも遡って付く**(「50ターン以内」を 60 にしたら、55ターンで
  勝った過去の回にも付く)。
- **すべての集まりに実績を1つ以上。** `test/progress.test.js` の
  「すべての集まりに実績がある」が `meets.js` の一覧と突き合わせるので、
  遊びを足して実績を忘れるとテストが落ちる。
- しきい値は**実測して決める**。CPU を6人入れて大会を回し、点の分布を見る
  (釣り大会 428〜663cm・蛮族 98〜141点。実績はその上位を超える線)。
  対戦のほうは自己対戦を回して `marksOf` の分布を見る(スクラッチパッドの
  `feasible.mjs`)。600 戦での到達率:
  都市国家 70% / 竜の宝 85%(銅)、極めし者 16% / 島の守護者 11% /
  街道王 8% / 二大都市 6%(銀)、大船団 16% / 騎士団 3% / 島から島へ 1%(金)。
- **「自分では寄せられない実績」は割合がそのまま理不尽さになる。** 船を
  並べる・騎士を出すは狙って寄せられるので到達率が低くても手が届くが、
  **勝つまでのターン数は4人ぜんぶのペースで決まる**ので寄せようがない。
  「50ターン以内に勝つ」は全体 3%(都市と騎士・航海者では 0%)で、銀なのに
  金より珍しかった ── 60 に緩めて 12%(いちばん速い漁師たちの島なら 27%)。

##### 席ごとに違うものを配る(大富豪だけ)

手札は隠し情報なので、全員に同じ表を配ると相手の手が丸見えになる。
`MeetCore` に `perSeat` / `viewFor(seat)` を足して、**立てた遊びだけ**接続ごとに
作る ── 竜は秒10回配るので、いつも宛先ごとに作り直すと人数の二乗ぶんの手間になる。

伏せ処理そのものは `src/minigame/daifugo.js` の `viewFor` 1か所に閉じている。
その戻り値は**そのまま判定の材料としても足りる**(ルール・場・革命・しばりが
入っている)ので、クライアントは自分の手札だけで「出せるか」をサーバーと同じ
答えで出せる ── 出せない札を沈めて見せているのはこれ。決めるのはサーバー。

大富豪だけは終わりが時間ではなく**決着**で決まる。器は時間で動くので、
`_step` が「決着したら true」を返して早じまいさせている(制限時間は保険)。

## BGM(`audio/score.js` + `audio/bgm.js`)

音源ファイルなしの完全合成。先読みスケジューラで和音を生成し、
ドローン+パッド+撥弦+フルート+刻みを合成リバーブ(生成した IR で convolution)に通す。
iOS 対策で初回ポインタイベントから開始。ON/OFF は localStorage に保存。

### インタラクティブミュージック

**曲は場面に合わせて変わる。** 音源を持たない生成音楽なので、曲を切り替えるのではなく
「譜面の決めかた」を差し替える。

```
main.js  musicScene() ─→ 場面名(title/game/walk/fishing/dragonhunt/raid/logroll/daifugo)
         musicIntensity() ─→ 高まり 0〜1
              ↓ syncMusic()
bgm.setScene() / setIntensity()
              ↓ 次の和音の頭で
score.js  chordAt / chordDur / layerGains / melodyChance
              ↓
bgm.js    Web Audio で鳴らす
```

- **計算はレンダリングから切り離す。** `score.js` は Web Audio も DOM も触らない
  純粋な関数の集まりなので `node --test` で検証できる(`test/score.test.js`)。
  音そのものは耳でしか確かめられないが、「場面ごとに本当に違うか」
  「高まりが効いているか」「進行が巡回するか」は数で押さえられる。
- **場面ごとに別の曲想。** 旋法(どの音を使うか)・和音進行・和音の長さ・編成を
  丸ごと入れ替える。速さと編成だけ変えても「同じ曲の濃さ違い」にしかならないので、
  **旋法が入れ替わっていること自体をテストで押さえている**
  (押さえないと、全場面を同じ旋法にしても他のテストは全部通ってしまう)。
  主音は D にそろえてあるので、場面が変わっても転調したようには聞こえない。
- **切り替えは次の和音の頭で。** `setScene` は `wantScene` に積むだけで、
  `_pump` が次の和音を予約するときに初めて効く。曲の途中で切れない。
- **進行は4和音の輪。** 途中に主和音へ戻る形(I-V-IV-I)を書くと、輪の継ぎ目で
  主和音が2小節続き、対戦の場面なら 11 秒もパッドが動かない ──
  生成し続ける BGM ではここが「止まって」聞こえる。最後の和音は主和音以外にする。
- **対戦の緊張は「段」で切り替える**(`raceScene`)。いちばん進んでいる人が
  上がりに近づくと、平常 → 接近(残り3点)→ 王手(残り1点)と場面ごと入れ替わる。
  「自分が近い」ではなく「誰かが近い」で上げる ── 追う側にとっても張り詰める場面だから。

  | 段 | 旋法 | 進行 | **BPM** | 和音 | 刻み | 旋律 |
  |---|---|---|---|---|---|---|
  | 平常 | ドリアン | grand | 66 | 6拍 | なし | 0.6 |
  | 接近 | ドリアン | drive | 114 | 7拍 | 1.9/秒 | 0.2 |
  | 王手 | エオリア | drive | 169 | 8拍 | 5.6/秒(裏拍あり) | 0.1 |

- **テンポは `bpm`。和音の長さではない。**
  最初は「和音1つの長さ(dur)」だけを持っていて、拍は bgm.js が 0.7 秒に
  固定して打っていた。和音を詰めても**1和音あたりの拍数が減るだけ**で、
  実測の拍は 86 → 83 → 88 BPM とほぼ動いておらず、
  段を切り替えても「速くなった」とは聞こえなかった(遊んだ人の言葉で
  「全然わからん」)。いまは `bpm` と `beats` を持ち、
  和音の長さは `beats × 60/bpm` で導く。刻みもハープもこの拍に乗せる。
  **和音は必ず拍の整数倍**にする ── そうでないと和音の変わり目で拍がずれる。

- **濃さを 0〜1 で連続に動かすだけでは耳に届かない。** 段に分ける前はそう
  作っていたが、旋法・和音進行・音域が最後まで同じで、動くのは音量バランス
  だけだった(しかも `base + add` が 1 を超えるパートは頭打ちで、宣言したぶん
  動いていなかった)。人は勾配ではなく出来事に気づく。

- **段が耳に届く大きさか、実際の波形で確かめる。** 譜面の数字ではなく、
  `master` に解析器を挿して測る。測りかたに落とし穴が3つあった ──
  (1) 立ち上がりの数え上げは `requestAnimationFrame` の間隔(3D描画に律速されて
  7fps)に左右されるうえ、閾値越えの回数はハープの密度を拾うので、
  刻みの無い場面でも 6打/秒と出てテンポ計にならない。`setInterval` で
  等間隔に取り、**包絡線の自己相関**で周期を出すこと。
  (2) 自己相関は正規化しないと長いラグほど大きく出て、和音の周期を
  「拍」と誤検出する。拍としてありうる範囲(0.15〜0.9秒)に絞る。
  (3) しきい値を勘で置かない。基準の切り替え(散策 → 各ミニゲーム)を測ると
  散策 → 蛮族は揺れ 1.15倍しかなく、勘で置いた 1.3倍は基準自身が通らなかった。
  自己相関の値は実行ごとに揺れる(同じ場面で 0.07〜0.23)ので、
  向きを見る道具であって精密な計測器ではない。

- **盛り上げたい段ほど持続音は減らす。刻みは持続音より前に出す。**
  これで三度つまずいた(王手・接近・竜)。「盛り上げたいから全部を最大に」
  すると、ドローンとパッドが拍を覆って逆に聞こえなくなる。竜は
  ドローン 1.0 / パッド 0.8 に対して刻み 0.85 で、狙った拍での相関が
  0.02 しかなかった(刻みが前に出ている蛮族は 0.31)。
  `test/score.test.js` が「刻み ≥ ドローン・パッド」を不変条件として押さえている。
- **刻みのある場面で音域を下げない。** 王手と竜を 1 オクターブ下げていたが、
  和音・ドローン・刻みが同じ低い帯域に集まって濁り、狙った拍での相関が
  0.02〜0.04 まで落ちた ── いちばん刻んでほしい場面で拍が埋まる。
  不穏さ・張り詰めは旋法と速さで出す。
- **打音の減衰は自分の間隔に収める。** 0.26 秒に固定していたので、
  王手の 0.178 秒間隔では前の打音の尾に次が重なって一続きの低音になっていた。
- 旋律を引っこめる(笛が歌うのをやめる)のがいちばん効く ── これを動かして
  初めて、平常 → 接近 の差が基準の切り替えに並んだ。
- **刻みは残響をほとんど通さない**(`bgm.js` の `dry` バス)。
  3.2秒の大聖堂リバーブに 260ms の打音を入れると、拍ではなく響きの一部になる。
- **刻みの音程には下限がある**(`PULSE_FLOOR`)。素直に「和音の根音の1オクターブ下」に
  すると、音域を下げた場面(王手・竜)では 92Hz→55Hz まで落ちてスマホでは鳴らない。
- **高まりは公開されている点だけで作る**(`computePoints` の `includeHidden` は既定の false)。
  伏せた勝利点カードまで見ると、手札を見ていない人にも**音で漏れる**。
  オンライン対戦の伏せ処理(`viewFor`)と同じ話が音にもある。

## 足音(`audio/footsteps.js`)

「地面の素材 × 体の動き」から、鳴らす音の中身を組み立てる。実際に鳴らすのは
`sfx.js` の `step` ボイス。決めごとをこちらに分けてあるので、Web Audio の無い
`node --test` でも表の抜けや強弱の関係を検査できる。

音は**3層の重ね**でできている。`scuff`(こすれ)= 素材を決める帯域ノイズ、
`body`(体重)= ローパスしたノイズ、`grit`(粒立ち)= 音量を細かくギザギザに
振ったノイズ。

- **足音に音程を持たせない。これがいちばん大事。** 以前は体重の音を
  midi 指定の正弦波で鳴らしていた。オフラインで波形を測ると、
  **その正弦波だけで音全体のエネルギーの 81〜98% を占めていて**、
  素材を表しているノイズは 2〜19% しか聞こえていなかった。つまりどの地面を
  歩いてもほぼ同じ高さの音が鳴っており、遊んだ人の言葉で
  「どこを歩いても鉄の上を歩いてるみたい」になっていた。
  いまは3層ともノイズ由来で、音程を持つ部品はひとつも無い。
  `test/footsteps.test.js` が「どの層にも `midi` が無い」「ローパスの Q は
  臨界(0.707)以下」「体重の層が素材の層を潰さない」を押さえている。
- **素材の違いは「どの層があるか」で出す。** 帯域の中心をずらすだけでは
  落ち葉と砂の区別は付かない。落ち葉は粒が主役で体重の音が無い、砂は粒が
  ひとつも無いなめらかな摩擦音、締まった粘土は逆に粒が無く体重の音だけ、
  というふうに構造から変える(これもテストで押さえている)。
- **同じ波形を繰り返さない。** ノイズ源は1秒ぶんを使い回しているが、
  毎回頭から再生していたので、連続する2歩の波形の相関が **1.0000**
  (一字一句同じ音)だった。人の耳は寸分たがわず繰り返す音を機械の音と
  受け取る。いまは再生開始位置を毎回ずらしていて、相関は 0.3 以下。
- **「金属的か」は平坦さで測ってはいけない。** スペクトルの平坦さだと
  「鈍い音」と「音程がある音」を区別できず、丘(低くて鈍いだけ)を
  金属的と誤判定する。**山のてっぺんの -6dB 幅**で見ること ── 純音は 22Hz
  しかないのに対し、雑音は 100Hz 以上に広がる。物差しは必ず答えの分かっている音
  (純音・白色雑音・共鳴なしのローパス雑音)で校正してから使う。
- **測るときは何度も鳴らして中央値を取る。** 再生開始位置を毎回ずらしている
  ぶん、1回だけ測ると値が跳ねる(同じ設定で 7.2 と 12.2 が出た)。

## 水の音(`audio/water.js`)

足音と同じ作り(決めごとの表 + `sfx.js` の薄いボイス)。着水・浮きの
「ポチャン」・魚が暴れる音の3種。

**狙いは「本物らしさ」ではなく「効果音としての正しさ」。**
ここは本物に寄せようとして5回外した。物理をどれだけ正しくしても、
効果音としては別の話だった ── 実物の飛沫はほとんど雑音の塊で、短い一発
として鳴らすと「何の音か分からない濁り」にしかならない。効果音に要るのは
**0.1 秒で「水だ」と分かること**。水の合図としていちばん強いのは
「ポチャン」の**上がる音程**で、人はこの形を水として覚えている。
だから正しく作るのではなく、**この形をはっきり出す**。

層は3つだけ ── `splash`(明るい雑音、頭の数十 ms)/
`ploop`(**上がる音程。水の正体**)/ `sparkle`(高く短い滴、尾のきらめき)。
音程は BGM と同じ D ドリアに乗せる。規模は「大きいほど低く・長く・粒が多い」。

**破って怒られたこと(全部テストで押さえてある):**
- **低い音を下へ滑らせない。** ローパスした雑音を低いほうへ滑らせるのは
  **屁の音の作りかたそのもの**で、「うんちしてる感じ」と言われた。
  しかも帯域の分析が「低音が足りない」と出るたび、こちらはその層を
  大きくし続けていた ── 数字を見て耳で確かめないと、こうなる。
- **音程は上げる。下げない。** 下がる音程は水ではなく体の音になる
  (最初の版は 73Hz の正弦波を下げていて「ボヨン」)。
- **低くしすぎない。** 上がっていても低すぎれば下品な帯に入る。
- **粒は増やすほど水らしくならない。** ランダムな位相の正弦波は重ねるほど
  中心極限定理で**ただの雑音に収束する**。実測でも聞き分けられる粒は
  8〜11 個で頭打ちで、24 個から 280 個に増やしても一切増えなかった。
- **層を重ねない。帯域と時刻を分ける。** 重なると互いを埋めて
  「複雑なのに何も聞こえない」濁りになる(「音が喧嘩している」)。
- **短く。** 効果音は居座らない。

**テストで三度、逆のことを固定した。** 「泡は小さく保て」(水は泡そのもの
なのに)、「泡は数百個」(重ねると雑音になるのに)、「低い層は下へ滑らせろ」
(屁の作りかたなのに)。**物として正しいことと、効果音として正しいことは
別**で、テストに書くのは後者。`test/water.test.js` に理由ごと残してある。

測りかたの落とし穴:
- **エネルギーの割合で短い一撃は評価できない。** 1秒の音のなかで 50ms の
  破裂音はどれだけ大きくても数%にしかならない。**区間ごとの山の高さ**で見る。
- **粒は乱数で作るので、1回だけ測ると跳ねる。** 9回鳴らして中央値を取る。
- **耳で確かめる手が要る。** `OfflineAudioContext` で鳴らして WAV に
  書き出し、人に聞いてもらう(スクラッチパッドの `wav.mjs` / `iso.mjs`)。
  `iso.mjs` は層を1つずつ書き出すので、「どの層が原因か」を一度で切り分け
  られる ── 数字だけで追うと、今回のように何度も的を外す。

## あそびかたデモ(`src/demo/`)

「文章だと操作感が分からない」を埋めるための**自動再生デモ**。動画ファイルは持たず、
本物のゲームエンジンと本物の HUD をその場で動かして見せる(だから実装と絶対にずれない)。

```
台本(script.js) ── ビートの配列
   ↓ 1ビート = prep → 字幕 → 指でタップ → ui/action
再生エンジン(driver.js) ── host 経由でしか main.js に触らない
   ↓ host.patchState / setUi / act / boardPos
main.js ── 通常の refresh・dispatch・演出がそのまま動く
```

- **章**: `setup`(はじめの配置)→ `basic`(基本の手番)→ `cak`(都市と騎士)。
  タイトルと説明書の各タブから開き、終わりに次の章へ送る。
  `setup` だけは `fromSetup: true` で初期配置の1手目から始め、CPU の配置も台本が1手ずつ進める
  (再生中は CPU の自動進行を止めているため)。
- **盤面依存の場所は台本に焼き込まない**。「どの辺に道を引くか」は毎回 `legalRoadEdges`
  などから選び直すので、盤面生成やルールが変わっても座標がずれない。
- **ルールエンジンには手を入れない**。出目の固定は既存の `turnFlags.alchemist`、
  イベントダイスは目的の面が出るまで `state.rng` を空回しして合わせる。
  発展カードを見せたいときは `stackDevDeck` で山札を**並べ替える**だけ(枚数構成は本物のまま)。
- **資源の配布は必ず銀行から**(`ensure` / `trimHand`)。保存則を壊さない。
- **HUD を変えたら台本も見直す**。台本は実物のボタン(`data-act`)とダイアログを指しているので、
  ボタンの追加・改名や新しいダイアログはそのまま「古い動画」になる。
- 再生中は `demoRunning` で CPU スケジューラを止め、全面シールドで人の入力も遮る。
- `test/demo.test.js` が台本をブラウザ抜きで空回しし、
  **全ビートの手が validate を通ること**と保存則を検証する。

## 戦績と実績(`progress.js` / `achievements.js`)

やりこみ要素。**端末のローカルに閉じる**(オフラインで遊べるアプリなので、
サーバーには送らないし、送らなくても成立する形にしてある)。

- `progress.js` は localStorage を触るのが `load/save/clear` だけで、
  集計(`summarize`)と記録(`addResult`)は純粋関数。
  テストが localStorage なしで全部書ける。
- **実績の判定はルールエンジンに手を入れない**。判定材料は
  「終局時の state」と「累計の戦績」だけに限る ── ゲーム中にカウンタを足すと
  既存の挙動(回帰ハッシュ)が揺れるので、そこには触らない。
  逆に言うと「1ターンに進歩カードを3枚使う」のような、state に残らない実績は作れない。
- しきい値は**実測して決める**。CPU 同士を各モード30戦回して分布を取り、
  到達不能な数字(例: 「25ターン以内に勝利」← 実際の中央値は70〜92)を避ける。
  `scripts/` には置いていないので、必要になったらスクラッチパッドで測り直す。
- 実績の書き方は2通り。**数値もの**は `{ mark, goal }` を宣言するだけで、
  判定も進捗表示(「11/13隻」)も共通の仕組みが面倒を見る。
  それ以外だけ `check(ctx)` を書く。
- 進捗には過去の最高到達値が要るので、対戦記録に `marks`(その対戦での到達値)を
  焼き付け、`summarize` が `bests` として最大値を取る。
  **state を読むのは `marksOf()` だけ**で、以降は marks しか見ない。
- 実績はフィールド名を1文字間違えても「静かに解除されないだけ」で気づけない。
  数値ものは `test/progress.test.js` が **全件を機械的に** 走査して
  「目標値なら解除される / 1足りなければ解除されない」を確かめている。
- **称号**が実績の見返り。実績1つにつき称号1つが紐づき、獲得したものから
  1つ選んで名乗る。対戦中は自分の名前の横と手番の合図に出る
  (モバイルはプレイヤー行が畳まれるので、合図のほうが本命)。
- 記録は1対戦につき1回。終局は毎フレーム通るので、
  `recordedState === state` で二重記録を防ぐ(新しい対戦なら別オブジェクトになる)。
- オンライン対戦は数えていない(席の入れ替わりや観戦があるため)。

## ミニゲーム「島を歩く」(`src/minigame/`)

対戦とは関係なく、島の上を棒人間で歩き回れるモード。

- **既存の島にそのまま相乗りする**。海・空・木・港・建物は Board3D が作ったものを
  使い、足すのは棒人間・追従カメラ・操作だけ。
  **レンダラーと requestAnimationFrame も Board3D のものを共有する**
  ── WebGL コンテキストを2つ持つとモバイルで重すぎるため。
  割り込み口は `Board3D.onFrame`(1フレームごとに呼ばれる)1つだけ。
- **カメラは Board3D と取り合わない**。`controls.enabled = false` は
  「入力を受けない」だけで、`controls.update()` は damping でカメラを
  動かし続ける。そのまま呼ぶと歩行モードのカメラ操作と毎フレーム
  取り合って画面がガタつくので、**`onFrame` がいる間は
  `controls.update()` を呼ばない**(カメラを持つのは1人だけ)。
- **カメラは足元の座標を追う**。描画上のモデル位置を追うと、
  歩行アニメーションの上下がそのまま画面の揺れになる。
  高さも**ならしたほう**(`motion.footY`)を使うこと ── 地面の生の高さは
  数字トークンの縁で階段状に跳ぶので、体だけならしてカメラが生を見ていると、
  そこでカメラと視線が一瞬で動いて画面が跳ねる。
- **追従はフレームレートに依らない式で**。`dt` を直に掛けると
  低フレームで係数が 1 を超えて瞬間移動になる(`1 - exp(-k·dt)` を使う)。
  歩く側とカメラ側で `dt` の刻み方を変えないこと ── 片方だけ刻むと
  「本人はゆっくり・カメラだけ瞬間移動」になる。
- **物理エンジンは使わない**。一度「ばねで行き過ぎさせてぐらつかせる」
  実装にしたが、画面が揺れて見づらいだけだったのでやめた。
  いまは手足を交互に振るだけの素直な歩行アニメーション。

- **歩きは「接地した足が地面の上で止まる」ことを軸に作る**(`pose.js`)。
  ここが崩れると「滑っている」と即座に見抜かれる。実測で、進んだ距離の
  **93%** を足が滑っていた(= ほとんど接地していなかった)。原因は3つ:

  1. **体が浮いていた。** 脚を θ 振ると足先は上がるので、そのぶん腰を
     下げないと両足とも宙に浮く ── 1周 16 コマのうち接地は 2 コマだけだった。
     `walkPose` の `lift` で、**低いほうの足がぴったり地面に着く量**だけ
     体ごと下げる。歩きの上下動もこれで自然に出る
     (カメラは motion の座標を追っているので画面は揺れない)。
  2. **膝を曲げる位相が 1/4 周ずれていた。** 振り出しかどうかは足の
     *位置* ではなく *動く向き* で決まる(rootX を微分する)。ずれていたため
     **接地した足が前へ動いて**いて、いちばん滑って見える形になっていた。
  3. **1歩の形を速さで縮めていた。** 縮めると歩幅だけ短くなって滑りが増える
     ── 遅いほど悪化していた(93% → 98%)。速さは**歩数**が受け持ち、
     1歩の形は変えない。

  直したあと 44%。残りは**速さと脚の長さの釣り合い**で、この体格
  (脚 0.059)では、滑りを 0 にするのに秒 11 歩いる。

- **歩数を上げすぎると、今度は画面が振動する。** 足を地面に着けるには
  脚を振ったぶん体が沈む(上の 1.)ので、**1歩ごとに体が上下する**。
  歩幅を詰めて秒 6.4 歩にしたとき、沈みの**大きさ**は背丈の 7.1% と
  人の歩き(5% 前後)並みだったが、**回数**が秒 6.4 回 ── 人の 2 回に対して
  3 倍で、遊んだ人から「画面がガクガクして疲れる」と言われた。
  歩数は `WALK_SPEED / STEP_DIST` なので、落とすには
  **歩く速さを下げるか、歩幅を伸ばして滑りを増やすか、脚を伸ばすか**しかない
  (この3つ以外に手は無い)。散策なので歩く速さを 1.9 → 1.25 に落とし、
  秒 4.2 歩にした。あわせて沈みを 7 割だけ効かせて(`BOB_KEEP`)背丈の 5.0%
  に収めている ── 引き換えに接地している足が 0.0055 浮くが、
  直す前の 0.024 よりはずっと小さい。

  **ただし今度は「遅い」と言われた。** 1.25 だと島の端から端に 11.1 秒
  (外周1周 35 秒)かかる。速さと歩数が一本の紐でつながっているのがつらい
  ところで、答えを2つに分けた:
  - 歩きは **1.25 → 1.45**(秒 4.9 歩、端から端 9.6 秒)まで。
    **脚の運びは1ミリも変えていない** ── 歩幅も沈みの深さもそのまま。
  - 足りないぶんは**駆け足**(`RUN_SPEED` = 2.4、端から端 5.8 秒)。
    駆け足では**歩幅のほうを伸ばす**(`pose.js` の `RUN_SWING` / `RUN_SLIP`)
    ので、速さが 1.65 倍でも歩数は 4.9 → 5.6 にしか増えない。
    伸ばさないと秒 8 歩になって、まさに上の「画面が振動する」に戻る。
    `strideOf(gait)` / `phasePerUnit(gait)` が歩きと駆け足を混ぜていて、
    **gait 1 までは歩きの値そのまま**(`test/run.test.js` が見張っている)。

- **止まったら足をそろえる**(`pose.js` の `restBlend` / `REST_IN`)。
  歩きの位相は止めるだけなので、そのままだと**片足を前に出した形で固まる**
  (実測で左右の脚が 0.264 ラジアン開いたまま突っ立っていた)。
  止まっているあいだ立ち姿(`standPose`)へ 0.26 秒かけて寄せ、歩き出したら
  0.10 秒で抜ける ── **入るより抜けるほうを速く**。押してから足が出るまでに
  間があると操作が重く感じるので、そこは削れない。
  **散策部屋の他の人にも同じものを付ける**(`remote-view.js`)── 付け忘れると、
  相手だけ片足を前に出したまま立って見える。

- **駆け足に入る合図はボタンではない。** スティックは元からアナログ
  (倒し具合 = 速さ)なので、**全倒しを 0.45 秒続けたら**駆け足に入る
  (`RUN_STICK` / `RUN_DELAY`)。ちょっと動かす操作は今までどおりの歩き、
  遠くへ行きたいときだけ勝手に速くなる。キーは押しっぱなしが全倒し。
  - **遊びの最中は切る**(`walk-mode.js` が `motion.runSpeed = null`)。
    竜は歩きの 0.82 倍、CPU は 0.88 倍と、**どれも歩く速さを基準に
    釣り合いを取ってある** ── 駆け足のまま逃げられると竜は振り切り放題、
    大会は勝ち放題になる。丸太も同じ(乗り手が丸太の流れを追い越して
    90 秒逃げ切ってしまい、実際にテストが落ちた)。

- **加速(`ACCEL`)に縮尺を掛けていた。** これは長さではなく「1/秒」の
  収束レートで、`scale.js` の決め(時間と角速度は掛けない)の側。
  `sc(9)` だったので全速の 95% に届くまで 0.65 秒 ── 最初の 0.5 秒で
  すぐ全速の場合の 63% しか進めず、ちょっと動かすたびに重かった。
  9 にして 0.32 秒。**空中の効きは「地上の何割か」で持つ**(`AIR_RATIO`)
  ── 絶対値のままだと、丸太の上だけ地上を鈍くしたときに空中の舵だけ
  2 倍効いてしまう。

- **丸太乗りだけは別の速さで歩く**(`logroll.js` の `ROLL_WALK`)。
  あちらは流れに押し負けまいと踏ん張る遊びで、手ごたえを丸太の回転と
  釣り合わせて実測してある。島に合わせて遅くしたら「うまく歩いても
  13 秒で落ちる」理不尽な盤になった。**歩く速さを変えるときは、
  それに乗っている遊びの釣り合いも確かめること** ── 丸太の回る速さは
  かつて 0.95 と焼き込んであり、危うく取り残されるところだった。

- **足の裏がどこに来るかは `solePos()` で出す**(`pose.js`)。
  「脚を θ 振ると足は L(1-cosθ) 上がる」で済ませようとしたが、靴が足首より
  前と下に付いているぶんが抜けていて、実機で測ると接地しているはずの足が
  0.012 上下していた。body.js の組み立てと同じ順で関節を辿る
  (寸法は `scale.js` が持つ ── body.js は THREE を使うのでテストから読めない)。
  実機のメッシュの世界座標と 0.0095 以内で一致することを確認済み。
  本物のラグドールには rapier などが要るが、500KB〜1MB+ あって
  ビルド工程なし + 全ファイルをプリキャッシュという作りと噛み合わない。
- **端では止めずに落とす**。海に落ちて1秒ほどで元の足場に戻る。
  止めるより遊びとして楽しく、詰まらない。
- 歩ける範囲の判定(`ground.js`)は THREE を使わない純粋な計算にしてあり、
  `test/minigame.test.js` が「ヘックスの中心に立てる/継ぎ目に落ちない/
  海には立てない」を全モードで確かめる ── 盤の幾何を1つ間違えると
  島の真ん中に穴が空くが、描画を見ただけでは気づきにくい。

- **ぶつかったら止まる。逃がすのは最後の手段**(`obstacles.js`)。
  木が2本近すぎる所へ一歩踏み込むと、順に押し出しても互いに打ち消し合って
  「まだ物の中」になる。そこで**先に**逃げ道(1つずつの縁の上で、行きたい所に
  いちばん近い触れない点)を探していたため、**離れた別の木の縁まで
  0.38 タイル = 1フレームの歩幅の 8 倍**飛んでいた ── 遊んだ人からは
  「島の中で謎にワープする」として報告された。
  立てる場所から踏み出したのなら、行き先が塞がっていても**来た場所に留まる**。
  逃げ道を探すのは、湧いた位置が物の中だったときだけ。その移動にも
  上限を置く(いちばん大きい物の「半径 + 体」の 2 倍 ── 自分に重なっている
  物は中心がその範囲にあるので、塊から出るにはこれで足りる)。
  上限が無いと、近くの縁がどれも塞がっているときに 3 タイル近く飛ぶ。

- **足元の高さは急に変えない**(`motion.js` の `FOOT_RATE`)。
  数字トークンの円盤は縁が垂直なので、地面の高さはそこで階段状に跳ぶ。
  実測で島じゅうの段差は**全部**トークンの縁(455/455、ヘックスの継ぎ目は
  0 か所)で、1フレームに 0.0416 上下していた ── 跳躍の高さの 2 割。
  縁をまたぐたびに体が瞬間移動し、縁沿いを歩くと上下に振動する
  (「描画がガチャガチャになる」として報告された)。
  上限は**本物の坂では効かない**ように決める ── いちばん急な地形(山)は
  0.419 高さ/タイル、歩く速さで 0.398 高さ/秒。その倍(0.8)にすれば
  坂は素通りで、段差だけが 4 フレームかけて登る「縁石をまたぐ」動きになる。
  瞬間移動(復帰・席へ着く・釣り場へ立つ)のあとは `snapFoot()` で合わせ直す。

- **この2つは実機を総当たりして見つけた**。島じゅうの立てる点から8方向へ
  歩かせ、「1フレームで物理的にありえない距離を動いた」点を数える
  (スクラッチパッドの `scan-warp.mjs`)。**物の中から始めないこと** ──
  そこは人が立てない場所なので押し出されて当たり前で、本物のワープと混ざる
  (最初これで 4989 件の偽陽性が出た。除くと 123 件、直すと 0 件)。

### 島の上でできること

歩くだけでなく、島ごとに遊びが乗っている。**どれも「進行」と「見た目」を
分けてある** ── 進行(`fishing.js` / `archery.js`)は THREE も DOM も
知らない純粋な計算なので `node --test` で押さえられ、見た目(`*-fx.js`)は
それを映すだけ。`test/no-bare-imports.test.js` がこの分離を静的に見張る。

| 遊び | 場所 | 進行 / 見た目 |
|---|---|---|
| 釣り | 港の桟橋ぎわ(全ての島) | `fishing.js` / `fishing-fx.js`。釣れるものは `fish.js` の表 |
| 蛮族を射る | 浜の物見の櫓(都市と騎士) | `archery.js` / `archery-fx.js` |
| 大富豪 | 島の中心の円卓(基本) | `daifugo.js` / `table.js`。進行はサーバー |
| 丸太乗り | 沖に浮かぶでっかい丸太(航海者たち) | `logroll.js` / `logroll-fx.js` |
| 集まり(大会) | 島の中心の受付 | サーバー持ち(上の「散策部屋」の節) |

- **乱数はそれぞれ専用の種を持つ。** `state.rng` は絶対に回さない ──
  回すとオンライン対戦で全員の乱数列がずれる。
- **釣りに入るところは「寄せる」。**「釣りを始めるとガクってなる」という
  報告で、三つ一緒に飛んでいたのを直した(`FISH_SETTLE` / `_settleToSpot`)。
  - **本人**: 押した場所から足場へ瞬間移動していた。釣り場は半径
    `SPOT_RADIUS`(0.21)の内側ならどこからでも始められるので、身長の
    半分ほど飛ぶうえ、沖を向かせるぶん向きが最大 180° 裏返る
    (実測: 1コマで 0.20 単位・144°)。0.22 秒かけて詰める ──
    投げる動作の振りかぶり(`CAST_TIME` の 35%)とほぼ同じ長さにして、
    「寄りながら振りかぶり、構えてから投げる」に見せる。
  - **カメラ**: 位置を直に寄せていた(`lerp`)ので、本人のまわりを回らずに
    空間を突っ切り、頭のすぐそばを通るあいだ景色が振り回されていた。
    極座標(回り込む角度・距離・高さ)で寄せて、距離を保ったまま回り込む。
    寄せ始めは**いまカメラが居る場所**を極座標に直したところから。
  - **浮き**: `cast()` の時点で落ちる場所に置いていたので、まだ振りかぶって
    いるのに浮きだけ沖にあり、糸だけがあとから伸びていた。投げている間は
    竿先から落ちる場所へ山なりに飛ばす。糸の終点は浮きそのものにする
    (両方で `castK` を掛けると二重に縮む)。
  - **投げ終わりの姿勢**: 段(`cast` → `wait`)が変わった瞬間に、振り出し
    きった姿勢(`swing = -0.5`)から構え(0)へ1コマで落としていた。竿先が
    **0.15 単位 ── 身長の 1/3** 飛び、そこで動きがぶつりと途切れて見えた。
    `pose.js` の `CAST_RECOVER` で戻りをつなぐ(振り出しのあと 0.25 秒かけて
    構えへ戻す)。そのために `_fishFrame` は**姿勢に渡す進み具合だけ 1 で
    頭打ちにしない** ── 浮きと糸は落ちたところで止まるので、そちらは 1 まで。
    カメラの見る先(`FISH_AIM`)も段で 0.4 → 1 に飛ばしていたので、
    同じ進み具合でならす(視線が1コマで 4.1° 回っていた)。
    `test/fish-pose.test.js` が「切り替わりのコマだけ竿が飛んでいないか」を
    毎コマ見ている。
  - **残りの段も同じようにつないだ**(`fishPoseBlender`)。段が変わるたびに
    **直前に描いた姿勢**から `FISH_BLEND` 秒かけて混ぜる(`blendPose` は
    エモートの出入りで使っているものを流用)。混ぜる元が生の姿勢ではなく
    直前の出力なのは、混ぜている途中でまた段が変わるから(アタリ → 取り込みは
    1 秒とかからない)。**アタリだけ短い**(0.07 秒)── 竿がぐっと入るのが
    「いま合わせろ」の合図なので、なまらせると合図として弱くなる。
    実測(竿先が1コマに動く距離、ふだんは 0.0001〜0.0075):
    `wait → bite` 0.015 → 0、`bite → fight` 0.029 → 0、
    `fight → landed` 0.088 → 0、`cast → wait` 0.151 → 0.007。
  - **段差があるときだけ混ぜる。** 混ぜること自体にも動きがある
    (重みの立ち上がりが素の動きに乗る)ので、もともと繋がっている
    `cast → wait` まで混ぜると**かえって速くなる**(0.049 → 0.073)。
    段差の測り方に注意 ── 直前のコマと比べると、ふだんの動き(振りかぶりは
    1コマ 0.065 ラジアン)まで段差に見える。**同じ時刻で「前の段だったら
    どうだったか」を出して比べる**。
  - 竿を出し直すとき(`setRod(true)`)につなぎを白紙に戻す。忘れると
    2回目の投げが「魚を掲げた姿勢」から始まる。
  - **やめるときも同じ**(`rodOutro` / `ROD_OUT`)。釣りの構えと立ち姿は
    右腕で 2.15 ラジアン(123°)離れているので、`setRod(false)` で竿を消すと
    次のコマで腕が下まで落ちていた。0.45 秒かけて歩きの姿勢へ戻し、
    **下ろしきる手前(`ROD_FOLD`)から竿をたたむ** ── 腕が下がりきってから
    消すと、下向きの棒が1コマで消えるのがかえって目につく。
    戻す先は止まった姿勢ではなく**毎コマの歩きの姿勢**(やめた直後に
    歩き出せるので、止まった姿勢へ寄せると歩きと喧嘩する)。
    カメラも2つ直した: `camYaw` を釣りのカメラの角度から続ける(戻すと
    回り込んでいたぶん 43° 飛ぶ)、見る先の沖ぶん(`FISH_AIM`)を
    `FISH_AIM_OUT` 秒かけて本人へ戻す(戻さないと視線が1コマで 7.5° 回る)。
    実測: やめた次のコマの視線の回りが 4.3° → 0.7°、カメラの移動が
    0.097 → 0.014 単位。
- **丸太乗りは「動く足場」を地面の関数として出している。**
  海に**でっかい丸太が1本**半分沈んで浮いていて、みんなでその上に乗る。
  `WalkerMotion` は `groundAt(x, z)` を外から受け取る作り(`motion.js`)なので、
  回る丸太を「時間で変わる地面」として島の地面に被せるだけで、歩き・跳び・
  踏み外し・海に落ちる、が今までのコードのまま動く。足場が横へ流れるぶんは
  地面が返す `drift` を `motion.js` が足す(`carry`)。
  - **丸いことも地面の高さで表せる。** `WalkerMotion` の `y` は「地面からの
    高さ」なので、地面が返す `y` を曲面(`軸 + R cos a`)にすれば、乗っている
    人は勝手に曲面をなぞる ── 坂の計算はどこにも要らない。
  - **軸を海面に置き、歩ける帯は水面まで届かせる。** 丸太は半分沈み、水から
    出ているところがそのまま足場になるので、足場の切れる角と水に落ちる場所が
    一致する。**内側で切ってはいけない** ── 切ったところから水面までが
    「見えているのに立てない」帯になり、そこが**見えない棚**として働いて、
    落ちた人が空中を歩いて丸太へ戻れてしまう(実測: 達人が永久に落ちなかった)。
  - **てっぺんを外れたら滑り落ちる**(`slipRate`)。これが無いと、丸太が
    丸いことがそのまま「端のほうが安全」になる ── 回転が横へ運ぶ速さは
    水平で見ると `spin × R × cos(a)` で端ほど弱まるのに、歩く速さは水平で
    測るので変わらないため、端へ行くほど押し返しやすくなってしまう。
  - **足元が抜けた時点で脱落**(`walk-mode` の `_watchDrumFall`)。跳んだの
    ではなく足場が消えたときは、そこで終わり ── 沈みきるのを待つと、
    水中で漕いで戻れる(抵抗は横の動きを弱めるだけ)し、切れ目が回り過ぎて
    足場が戻ってくると着地し直せる。落ちた人はどこに着いても岸へ返す。
  - **丸太のまわりに広い海の余白を取る**(`COURSE_CLEAR`)。足りないと
    端から落ちた人が隣の小島に降り立つ ── 水に触れないので脱落にならず、
    その小島は歩いては出られないので回のあとで詰む(実測: 余白 0.66 では
    どの盤でも縁から陸まで 0.95 タイルしかなく、ジャンプで届いていた)。
  - **切れ目と切れ目のあいだに「歩ける角」を残す**(`FREE_TURN`)。
    切れ目が上に居るあいだはまたげないので、角の間隔が切れ目の幅ぎりぎり
    だと、1つ目をよけた足でそのまま2つ目へ踏み込む ── 腕前によらず数秒で
    落ちる回ができる(実測: 先読みを 1.0〜3.2 秒のどれにしても 8〜17 秒で
    落ちる盤があった)。`safeZ` も**切れ目をまたがずに行ける先**を返す。
  - **切れ目は角を離して置く。** 同じ角に2つ来ると丸太を横切ってしまい、
    何をしても落ちる回ができる。角を等分した帯に1つずつ、帯より狭く振ると
    **ある瞬間に効く切れ目は高々1つ**になり、長さ方向の逃げ場が必ず残る。
  - **回る速さは上げていき、最後は歩きより速くする。** 上面の流れが歩きを
    超えないと、スティックを倒しておくだけで誰も落ちない(歩きの 71% で
    止めていたときは、腕前 7 割・反応 0.3 秒の人でも 90 秒逃げ切った)。
    速さが変わるので、回った角は `spin × t` ではなく**積分**(`turnAt`)で
    持つ ── でないと速さを変えた瞬間に丸太が飛ぶ。
  - **CPU も人と同じ壁に当てる。** 「押されるぶんの○%を打ち消す」で書くと、
    %が小さい子はいつまでも落ちず、人がどれだけうまく乗っても勝てない相手が
    できる。CPU も「歩く速さの上限まで押し返す」と書けば、流れが歩きを
    超えた時点で人と一緒に落ちていく。
  - **手ごたえは実測して決める。** 腕前と反応の遅れを変えた人を実際に
    `WalkerMotion` で乗せて、何秒残るかを見る(スクラッチパッドの
    `tune-roll.mjs`)。いまは「へた 13秒 / ふつう 40秒 / うまい 57秒 /
    達人 65秒」、CPU は 17〜52秒。**誰も 90 秒は残らない**ので勝負が決まる。
  - **高さの基準を混ぜない。** `motion.js` の `WATER_Y` はタイル上面からの
    相対値、`ground.js` の `makeGround` が返す `y` は世界の高さ。混ぜると
    「画面の丸太に乗っているのに足だけ沈む」ことになる。
  - **見た目の回転は THREE の回り方に合わせる。** `Object3D.rotation.y` は
    `logroll.js` の `toWorld` と逆回りなので、丸太の向きには `-anchor.angle` を
    入れる。ここを落とすと、丸太の中心は合っているのに長さ方向だけ開いて、
    「何もないところで落ちる」丸太が描かれる。
  - **見た目に足すものは切れ目で切る。** 木肌の筋を全長に通したときは、
    開いた切れ目の上に筋が板のように浮いた。飾りを足すなら足場と同じ
    区切りで切るか、足さずに済ませる(いまは分割を粗くした平面シェーディング
    の面の移り変わりで回転を見せていて、メッシュを1枚も足していない)。
  - **丸太の上ではカメラを回り込ませない。** 丸太の上で歩くのは主に太さ方向
    なので、歩いた向きへカメラを回すと丸太を真横から見る絵になり、長さ方向の
    どこに切れ目が来ているかが映らない。向きを長さ方向へ固定しておくと、
    スティックの上下が「切れ目をよける」、左右が「流れに逆らう」に決まる。
- **集まりには CPU を混ぜられる(`src/minigame/meet/cpu.js`)。**
  何人入れるかは**オーナー**(部屋のホスト。ひとりで歩くときは自分)が受付で決める。
  CPU は**部屋の空いている席に座る**ので、順位表も名簿も名前もすがたも、
  人の席とまったく同じ道を通る ── 席は**後ろから**詰めて、前から座らせる
  部屋(`room-core.js`)とぶつからないようにしてある(それでも重なったら CPU が退く)。
  部屋のほうには CPU を知らせない ── 知らせると、集まりの都合で部屋の席が埋まる。
  **体を島の上に出す。** 順位表に名前が並ぶだけだと、誰も居ない島で数字が伸びる
  ことになる。歩く地面の判定も、円卓・桟橋・櫓の場所も、人が使うのと同じ
  `ground.js` から出るので、CPU だけ海の上を歩いたり卓からずれて座ったりしない。
  位置は散策部屋の中継に混ぜて配る(`room-do.js`)ので、描くのは
  `remote-view.js` ── 人を描くのと同じ道。
  大富豪の CPU は**放置よけ(`autoPlay`)を借りない。** あれは「席を外した人の
  代打」で場があれば必ずパスするため、相手にすると人がひとりで出し続けて必ず勝つ。
  CPU は `weakestPlay` で出せる手のいちばん弱いものを出す(`cpuMove`)。
- **ひとりで歩くときは、集まりの進行を手元で回す(`src/minigame/meet/local.js`)。**
  エンジンはもともとトランスポート非依存なので、サーバーと同じものをそのまま
  `setInterval` で回すだけ。自分は席0(`SOLO_SEAT`)。クライアント側の送り口は
  `meetSend` 1本にまとめてあり、オンラインならサーバーへ、ひとりなら手元の器へ
  同じ形で流す ── 呼ぶ側が「いまどっちか」を気にすると、片方だけ直したときに
  静かに効かなくなる。
- **ひとりで歩くときは、島えらびの画面(`walkset`)で島と種を決める。**
  歩く島は `makeWalkIsland(seed, mode)` が作る ── 散策部屋と同じ入口。
  ここを設けるまでは、タイトルの飾りの盤(`showTitleBoard` が `mode:'cak'`
  で作る)をそのまま歩いていたので、**タイトルから歩くと必ず都市と騎士の島**
  だった。対戦の設定(`settings`)とは分けてある(歩くのに CPU の数は要らないし、
  歩くために選んだ島で次の対戦が始まっても困る)。
  何が乗っている島かは `meet-guide.js` の `islandNoteHtml` が1行で出し、
  `test/meet-guide.test.js` が**実際に島を作って**書いてあることと突き合わせる。
- 櫓や受付のまわりは木や岩を片付ける(`POST_CLEAR` / `DESK_CLEAR`)。
  海のほうに物を置かないのは、構える高さが地面から 0.11 しかなく、
  低い物でも射線を塞ぐため。片付けた木は島を出るときに戻す。
- 記録と実績は端末のローカル(`progress.js`)。図鑑・自己最高・大会の通算を持つ。
- **あそびかたは `src/render/meet-guide.js` の1か所。** 島を歩く HUD の ❓ は
  その島のぶんだけ、説明書の「🎪集まり」タブは全部を出す ── 同じ文章を
  2か所に書かない。操作は画面のどこにも出ていないので(「押している間だけ
  弓を引く」等)、ここが実質の操作説明になる。制限時間の数字はサーバーの
  定数を書き写しているだけなので、`test/meet-guide.test.js` が両方を
  突き合わせて、ずれたら落とす。
- 円卓の席の並び(`ground.js` の `tableSeats`)も THREE を使わない計算にしてある。
  **卓の見た目と、座る位置と、天板の札の向きが同じ式から出る**ので、各自が
  自分を座らせるだけで相手の画面にも同じ席に座って見える。
  寸法の前後関係(腰かけの輪 < 卓に届く距離 < 降り立つ輪)は
  `test/minigame.test.js` が見張っている ── ここが崩れると、島に降りた瞬間から
  受付のパネルが開くか、席を立った人が卓から離れた扱いになる。
